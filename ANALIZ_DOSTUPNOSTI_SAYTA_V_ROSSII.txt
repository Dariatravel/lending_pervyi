АНАЛИЗ ПРОБЛЕМЫ ДОСТУПНОСТИ САЙТА АБХАЗБЕРЕГ В РОССИИ
Дата проверки: 8 августа 2026 года

Цель
Понять, почему часть клиентов из России периодически видит полностью белую
страницу при открытии сайта https://абхазберег.рф/, хотя у владельца и у части
других пользователей сайт работает нормально.


1. КРАТКИЙ ВЫВОД

Наиболее вероятная причина — не ошибка конкретной карточки объекта и не
фотографии. Основная уязвимость заключается в архитектуре размещения:

- фотографии и видео уже находятся в Yandex Object Storage;
- HTML, CSS, JavaScript, JSON, шрифты и другие файлы самого сайта по-прежнему
  отдаются через GitHub Pages;
- домен абхазберег.рф указывает на IP-адреса GitHub Pages/Fastly:
  185.199.108.153
  185.199.109.153
  185.199.110.153
  185.199.111.153

Поэтому пользователь должен сначала успешно получить страницу и оформление с
GitHub. Только после этого браузер начинает показывать медиа из Яндекса. Если
доступ к GitHub у конкретного российского оператора зависает или работает
нестабильно, пользователь видит белую страницу, несмотря на исправную работу
Yandex Object Storage.

Нельзя утверждать, что домен сайта официально заблокирован. Проверка указывает
на выборочную и периодическую сетевую/DNS-проблему на пути к GitHub Pages.


2. ЧТО ПРОВЕРЕНО

2.1. Домен и DNS

- Авторитетные DNS-серверы: ns1.reg.ru и ns2.reg.ru.
- Оба сервера корректно возвращают четыре IP-адреса GitHub Pages.
- Google DNS, Cloudflare DNS и Yandex DNS во время проверки также возвращали
  правильные записи.
- DNS-записи соответствуют официальной схеме GitHub Pages.
- Отсутствие AAAA-записей само по себе не объясняет белые страницы: IPv4 есть и
  работает. Добавление IPv6 не устранит зависимость от GitHub.

2.2. HTTPS-сертификат

- Сертификат для punycode-домена xn--80aacbklan7f0b.xn--p1ai действителен.
- Имя домена входит в сертификат.
- TLS-соединение устанавливается корректно.
- Ошибка сертификата не является причиной текущих жалоб.

2.3. Страница и код

- Проверенная страница отеля возвращает HTTP 200 и полноценный HTML.
- В контрольном браузере страница отрисовалась нормально.
- Заголовок, текст, CSS и фотографии появились.
- Ошибок JavaScript в контрольном браузере не обнаружено.
- HTML содержит полезный контент ещё до выполнения JavaScript, поэтому
  постоянная программная ошибка приложения маловероятна.

2.4. Проверка из российских сетей

Была выполнена внешняя HTTP-проверка через российские сетевые точки.

- HTML страницы открылся из пяти российских точек, включая МТС.
- При отдельной проверке CSS через МТС в Новосибирске запрос завершился ошибкой.
- При отдельной проверке JavaScript через ту же сеть МТС ошибка повторилась.
- Зафиксировано: queryA ENODATA для домена сайта.
- Одновременно фотография из Yandex Object Storage через российскую сеть МТС
  открылась с HTTP 200.
- Через Ростелеком, ER-Telecom и несколько других российских сетей CSS и
  JavaScript в момент проверки открывались.

Это подтверждает выборочный характер проблемы: одна сеть может не получить
файлы сайта, в то время как Yandex Object Storage в той же сети работает.

3. ПОЧЕМУ ПОЛЬЗОВАТЕЛЬ ВИДИТ БЕЛУЮ СТРАНИЦУ

3.1. HTML и CSS зависят от GitHub Pages

Файл styles.min.css подключён в секции head как обычная таблица стилей. Такая
таблица является блокирующим отображение ресурсом. Пока браузер ждёт CSS, он
может не показывать содержимое страницы. Если соединение с GitHub зависло, а не
завершилось быстрой ошибкой, на экране долго остаётся белый фон.

Если завис сам первый запрос HTML, результат будет таким же: адрес уже виден в
браузере, но содержимое ещё не получено.

3.2. Service worker не имеет сетевого тайм-аута

На сайте зарегистрирован service worker /sw.js. Для HTML используется стратегия
network first: сначала ожидать сеть, затем при ошибке искать копию в кеше.

В текущей реализации нет собственного короткого тайм-аута. Если оператор не
отклоняет соединение, а оставляет его зависшим, переход может ждать слишком
долго. Резервная копия включается только после фактического исключения fetch.

Кроме того, карточка объекта, которую человек открывает впервые, обычно ещё не
лежит в кеше. Поэтому даже корректный fallback не поможет новому посетителю без
заранее подготовленной резервной страницы.

Service worker, скорее всего, не является первопричиной сетевого сбоя, но может
увеличивать продолжительность белого экрана.

3.3. Медиа из Яндекса не решает недоступность самой страницы

Перенос фотографий и видео в российское хранилище выполнен в правильном
направлении. Однако браузер не может показать эти медиа без HTML и CSS. Сейчас
перенесён тяжёлый контент, но входная точка сайта всё ещё зависит от зарубежного
GitHub Pages.

3.4. Видео могут замедлять уже открывшуюся страницу

На некоторых страницах несколько видео имеют preload="metadata". На слабой
сети браузер может одновременно выполнять ряд запросов диапазонов к видео.
Это способно вызывать рывки и задержки после появления страницы, но не является
главным объяснением полностью белого экрана.


4. ЧТО НЕ ЯВЛЯЕТСЯ ОСНОВНОЙ ПРИЧИНОЙ

- Кириллическое имя абхазберег.рф. Внутри DNS оно штатно представлено в
  punycode и во время проверки разрешается корректно.
- Недействительный сертификат. Сертификат исправен.
- Сломанные фотографии. Проверенная фотография из Яндекса возвращает HTTP 200.
- Ошибка конкретной карточки отеля. Проверенная карточка содержит полноценный
  HTML и нормально отображается при доступной сети.
- Общая постоянная авария GitHub Pages. В момент проверки сервис работает у
  большинства точек, проблема выборочная и периодическая.


5. ОСНОВНОЕ РЕШЕНИЕ

Перенести в российскую инфраструктуру не только медиа, но и весь результат
публикации статического сайта:

- все index.html и страницы объектов;
- styles.min.css и scripts.min.js;
- JSON-каталог и данные карты;
- шрифты, иконки, manifest и service worker;
- 404.html и остальные необходимые статические файлы.

Рекомендуемая схема:

GitHub — хранение исходников и запуск автоматической сборки.
Yandex Object Storage — публичный хостинг готового статического сайта.
Yandex Certificate Manager — HTTPS-сертификат.
Yandex Cloud DNS — привязка корневого домена через ANAME.
Yandex Cloud CDN — опционально после проверки базового хостинга.

Путь российского посетителя после переноса:

Пользователь -> Yandex Object Storage/Yandex Cloud -> HTML, CSS, JavaScript и
медиа.

GitHub останется инструментом разработки, но перестанет участвовать в каждом
визите клиента.

Официальная документация Yandex Cloud:
https://yandex.cloud/ru/docs/storage/concepts/hosting
https://yandex.cloud/ru/docs/storage/tutorials/static/console


6. КАК ПЕРЕНОСИТЬ БЕЗОПАСНО

1. Не менять текущий DNS сразу.
2. Создать отдельный бакет для сайта, не смешивая его с существующим бакетом
   медиа без необходимости.
3. Настроить бакет как статический сайт: index.html и 404.html.
4. Загрузить копию опубликованного сайта.
5. Проверить MIME-типы CSS, JavaScript, JSON, шрифтов, изображений и видео.
6. Выдать только публичное чтение объектов; ключ записи оставить закрытым.
7. Выпустить сертификат и настроить временный тестовый поддомен.
8. Проверить главную, каталог, карту, подборки и разные типы страниц объектов.
9. Проверить сайт через несколько российских операторов.
10. Настроить автоматическую синхронизацию после успешной сборки в GitHub.
11. Только после проверки переключить основной домен.
12. Старую публикацию GitHub Pages временно сохранить как резерв, но не
    направлять на неё основной клиентский трафик.

Для корневого домена второго уровня Yandex Cloud DNS поддерживает ANAME для
статического сайта в Object Storage. Не следует без проверки направлять ANAME
на Cloud CDN: документация CDN предупреждает, что это может нарушить
географический выбор узла. CDN удобнее подключать после отдельного решения по
домену либо использовать прямой статический хостинг Object Storage на первом
этапе.


7. ДОПОЛНИТЕЛЬНЫЕ ИЗМЕНЕНИЯ В КОДЕ

После или параллельно с переносом желательно:

- добавить в service worker тайм-аут 4-6 секунд для HTML-навигации;
- при тайм-ауте отдавать кешированную страницу, а если её нет — понятную
  резервную страницу с кнопкой повторной загрузки и контактами;
- не кешировать как успешную пустую HTML-страницу;
- предусмотреть обновление/очистку старых кешей service worker;
- заменить preload="metadata" на preload="none" у видео, которые находятся
  ниже первого экрана;
- использовать постеры видео и начинать загрузку только после действия
  пользователя;
- оставить адаптивные WebP-версии изображений и исходный JPG как fallback;
- не переносить изображения обратно на GitHub.

Эти изменения уменьшат последствия плохой сети, но сами по себе не устранят
зависимость первого визита от GitHub Pages.


8. МОНИТОРИНГ ПОСЛЕ ПЕРЕНОСА

Нужна регулярная проверка минимум из сетей:

- МТС;
- Ростелеком;
- МегаФон;
- Билайн;
- ER-Telecom/Дом.ru.

Проверять отдельно:

- DNS-разрешение домена;
- получение HTML;
- получение CSS и JavaScript;
- получение первой фотографии;
- время до первого отображения страницы;
- HTTP-коды и TLS;
- открытие новой, ранее не посещённой карточки объекта.

Важно проверять не только главную страницу. Кеш браузера или service worker
может скрыть проблему на уже посещённой странице.


9. ИТОГОВАЯ ОЦЕНКА

Вероятность основных причин:

Высокая:
- нестабильный доступ части российских сетей к GitHub Pages/Fastly;
- DNS/маршрутная нестабильность у отдельных операторов;
- ожидание блокирующего CSS или самого HTML с GitHub.

Средняя как усиливающий фактор:
- отсутствие тайм-аута и полноценного offline fallback в service worker.

Низкая:
- ошибка сертификата;
- кириллический домен как таковой;
- поломка фотографий в Yandex Object Storage;
- постоянная ошибка JavaScript на всех устройствах.

Рекомендация: считать перенос всего статического сайта в Yandex Object Storage
приоритетной инфраструктурной задачей. Изменения только в CSS, JavaScript или
кеше не смогут гарантировать доступность для нового посетителя, если первый
HTML-запрос продолжит идти на GitHub Pages.
