# Перенос сайта в Яндекс Облако

Дата составления: 3 августа 2026. Причина: гости из части регионов России не
могут открыть сайт. Хостинг — GitHub Pages (зарубежные адреса 185.199.108–111.153),
и доступ к ним у ряда российских операторов пропадает. Медиа у нас уже лежит в
Яндекс Облаке и открывается всегда — значит переезд туда снимает проблему целиком.

## Что переносим

Сайт статический: HTML, CSS, JS, шрифты, карты. Базы данных нет, серверного кода
нет. Это самый простой вид переезда — копирование файлов в бакет.

Медиа (фото и видео) переносить НЕ нужно: оно уже в
`storage.yandexcloud.net/abhazbereg-media/media/`.

## Куда именно

**Yandex Object Storage в режиме хостинга статического сайта** + **Yandex Cloud CDN**.

- Object Storage раздаёт файлы, как GitHub Pages сейчас.
- CDN нужен ради HTTPS на своём домене и скорости: без него бакет отдаёт сайт
  только по адресу вида `bucket.website.yandexcloud.net`.
- Сертификат для абхазберег.рф выпускается бесплатно в Certificate Manager.

Альтернатива — Yandex Cloud Compute (виртуальная машина с nginx). Не берём:
дороже, требует обслуживания и обновлений безопасности, а выигрыша для статики нет.

## Порядок работ

### Этап 1. Подготовка (1–2 часа, без влияния на живой сайт)
1. Создать бакет `abhazbereg-site` в том же облаке, где лежит медиа.
2. Включить режим хостинга: главная `index.html`, страница ошибки `404.html`.
3. Создать сервисный аккаунт с правом записи в бакет, выпустить статический ключ.
4. Положить ключ в GitHub Secrets (`YC_SITE_KEY_ID`, `YC_SITE_SECRET`).
5. Залить копию сайта и проверить её по временному адресу бакета.

### Этап 2. Автодеплой (1 час)
6. Добавить workflow: при пуше в `main` синхронизировать файлы в бакет
   (S3-совместимый API, `aws s3 sync --delete`), исключая `media/` и служебное.
7. Проверить, что после пуша изменения появляются на временном адресе.

### Этап 3. Домен (1–2 часа + ожидание DNS)
8. Создать CDN-ресурс, источник — бакет.
9. Выпустить сертификат для `абхазберег.рф` и `www.абхазберег.рф`.
10. Переключить A-записи домена с адресов GitHub Pages на адрес CDN.
11. Подождать обновления DNS (от 15 минут до нескольких часов у разных провайдеров).

### Этап 4. Проверка (1 час)
12. Прогнать `tools/check_site_availability.py` — сравнить картину по России
    до и после переезда.
13. Прогнать `post-deploy-smoke.yml` — страницы, WebP, видео, запреты.
14. Проверить в Яндекс.Вебмастере, что робот видит сайт и sitemap.
15. Неделю последить за целью `offline_page_shown` в Метрике: если офлайн-страница
    перестала показываться — проблема решена.

## На что обратить внимание

- **Service worker.** У гостей в браузере закэширована старая версия сайта.
  После переезда нужно поднять версию через `tools/bump_asset_version.py`,
  иначе часть посетителей несколько дней будет видеть старые страницы.
- **Кириллический домен.** В настройках облака он записывается в виде
  `xn--80aacbklan7f0b.xn--p1ai`. Сертификат выпускать на оба написания.
- **Регистр имён файлов.** Object Storage чувствителен к регистру строже, чем
  GitHub Pages: ссылка на `Karta.html` при файле `karta.html` перестанет работать.
  Проверить прогоном smoke.
- **GitHub Pages не отключать сразу.** Оставить как запасную площадку минимум
  на месяц: если в облаке что-то пойдёт не так, домен переключается обратно
  за минуты.
- **Стоимость.** Хранение статики — считанные рубли в месяц (сайт без медиа
  весит десятки мегабайт). Основная статья — исходящий трафик CDN; при нашей
  посещаемости это ориентировочно несколько сотен рублей в месяц. Точную сумму
  видно в калькуляторе облака после первого месяца.

## Ответы на вопросы к переезду (8 августа)

**Что синхронизировать в бакет.** Всё, что отдаётся гостю: `index.html`, папки
`hotels/`, `kvartira/`, `podborki/`, `blog/`, `karta/`, `styles.min.css`,
`scripts.min.js`, `pwa.js`, `sw.js`, `offline.html`, `404.html`, `data/*.json`,
`vendor/`, `app-icons/`, `app.webmanifest`, `sitemap.xml`, `robots.txt`.
Исключить: `.git/`, `scripts/`, `tools/`, `docs/`, `deploy/`, `output/`,
`media/`, `styles.css` и `scripts.js` (несжатые исходники), `*.md`,
`CODEX_TASK.md`, `CURSOR_TASK.md`.

**Адреса страниц.** Object Storage в режиме хостинга сам отдаёт `index.html`
для адреса, оканчивающегося на `/`. Наши адреса уже такие
(`/hotels/<slug>/`), поэтому ни редиректов, ни смены URL не потребуется —
для SEO переезд пройдёт незаметно. Проверить это надо на тестовом поддомене
до переключения домена.

**Чтобы не смешались новая страница и старое оформление.** У нас уже есть
защита: `tools/bump_asset_version.py` проставляет единый `?v=` на все ссылки.
Файл с новой версией лежит рядом со старым, они не затирают друг друга.
Порядок заливки: сначала статика (CSS, JS, шрифты), затем HTML, и только
потом `sw.js`. Удаление старого (`--delete`) — отдельным проходом на следующий
день, когда никто уже не держит старую версию открытой.

**Нужен ли CDN сразу.** Да, и это поправка к моему прежнему ответу. Я писала,
что на первом этапе достаточно Object Storage со своим доменом и сертификатом,
— это верно только для HTTP. **Object Storage отдаёт собственный домен без
HTTPS**: свой сертификат к бакету не привязывается, а встроенный выписан на
`*.website.yandexcloud.net`. Если направить `абхазберег.рф` прямо на бакет,
браузеры покажут гостям предупреждение об опасности — то есть будет хуже, чем
сейчас.

Значит цепочка такая: домен → Cloud CDN (с нашим сертификатом) → бакет.
CDN здесь не ускоритель, а единственный способ получить HTTPS на своём домене.
Замечание из документации про ANAME на CDN остаётся в силе и учитывается при
настройке записей.

**Тайм-аут в service worker.** Сделано 8 августа, до переезда — см. `sw.js`:
через 5 секунд молчания сети отдаётся кэш, через 15 — офлайн-страница;
запрос при этом не обрывается и обновляет кэш к следующему заходу. Пустой
HTML с кодом 200 в кэш не попадает. Логика проверена в
`scratchpad/sw_test.mjs` на четырёх сценариях.
Важная оговорка: **первому посетителю это не поможет** — service worker
начинает работать только со второго визита. Первый визит спасает только
переезд.

**Проверка после публикации.** Уже есть `post-deploy-smoke.yml`. На время
переезда его нужно натравить на адрес тестового бакета через переменную, а
после переключения домена вернуть на прод.

**Быстрый возврат.** GitHub Pages не отключаем минимум на месяц. Перед сменой
DNS выставить TTL записей в 300 секунд — тогда откат займёт минуты, а не
сутки. Возврат: вернуть прежние A-записи 185.199.108–111.153.

## Чего переезд НЕ решает

Если у гостя проблема не с хостингом, а со связью (слабый мобильный интернет,
сбой у оператора), переезд не поможет. Поэтому сначала — данные: прогон
`site-availability.yml` и статистика по цели `offline_page_shown` в Метрике.
Если окажется, что российские узлы открывают сайт нормально, причина в другом,
и переезд можно не делать.

## Домены-зеркала и ссылки для переписок (найдено 8 августа)

`abhazbereg.com` — не просто зеркало «на всякий случай». В `scripts.js` он
задан как `SHARE_ORIGIN`: **все ссылки, которые сайт даёт скопировать или
отправить, строятся именно на него**, а `normalizePublicUrlText` заменяет
кириллический домен на латинский в любом тексте (в том числе в сообщении
менеджеру из «Избранного»).

Отсюда следствие, которое меняет порядок работ:

> Гость, получивший ссылку в переписке, идёт на `abhazbereg.com`, то есть на
> GitHub Pages, и только оттуда JavaScript переносит его на основной домен.
> Переезд основного домена в Яндекс таких гостей НЕ спасает: первый запрос
> всё равно уходит на GitHub.

Для продаж через Telegram это, вероятно, самый частый путь захода — и ровно
тот случай, на который жалуются («отправили ссылку, у клиента белый экран»).

Состояние `abhazbereg.com` на 8 августа (проверено Codex, менять пока ничего
не нужно): GitHub Pages, HTTPS исправен, промежуточная HTML-страница с
`location.replace()`, путь и параметры сохраняются, ответ `200`, страница
закрыта от индексации, canonical на основной домен. Сертификат
`fpq57jgofcg721oapneo` латинский домен НЕ покрывает.

Два независимых пути это исправить, оба требуют решения Дарьи:

1. **Перенести переадресацию на российскую инфраструктуру** и сделать её
   серверной `301` с сохранением пути. Нужен отдельный сертификат на
   `abhazbereg.com` и `www.abhazbereg.com` либо новый сертификат с полным
   набором доменов. Ссылки остаются красивыми, латинскими.
2. **Сменить `SHARE_ORIGIN` на основной домен.** Ссылки пойдут сразу на
   `абхазберег.рф`, минуя GitHub вовсе, — это бесплатно и делается одной
   правкой. Плата за это: в переписках адрес местами показывается технической
   записью `xn--80aacbklan7f0b.xn--p1ai`, ради чего латинский домен и заводили.

Второй путь снимает проблему быстрее, первый — сохраняет вид ссылок. Можно и
оба: сначала второй как временная мера, потом первый.

У Дарьи есть и другие домены (`abhazbereg.ru`, `.info`, `.online`, `.store`,
`abhaz-bereg.ru`, `abhaz-bereg.online`). Если они тоже ведут через GitHub
Pages, их стоит проверить и перенести тем же способом.

### Препятствие

Рег.ру не даёт создать CNAME для корня `абхазберег.рф`. Это не каприз
регистратора: по стандарту DNS у корня зоны уже есть служебные записи (SOA и
NS), а CNAME по правилам не может соседствовать ни с чем. Обходной приём
называется ANAME (или ALIAS) — его поддерживают не все, и Рег.ру не
поддерживает.

У Yandex Cloud CDN нет постоянных IP-адресов: он раздаёт их через GSLB, поэтому
направить корень A-записями тоже нельзя — адрес меняется.

### Разбор вариантов

**А. Перенести зону `абхазберег.рф` в Yandex Cloud DNS.** Там ANAME для корня
поддерживается. Главный адрес сайта остаётся прежним, без www, — для поисковых
систем ничего не меняется.

Возражение Codex: документация Яндекса предупреждает, что ANAME на CDN лишает
географической маршрутизации. Возражение верное, но для нас малосущественное:
геомаршрутизация нужна, чтобы гостя из Владивостока и гостя из Берлина увести
на разные узлы. Наша аудитория целиком в России и Абхазии, и цель переезда —
не скорость, а сама доступность. Сайт всё равно будет отдаваться российскими
узлами, а это именно то, ради чего всё затевалось.

Настоящий риск здесь другой и он серьёзнее: **смена NS-серверов переносит всю
зону разом, включая MX-записи почты**. Если при переносе потерять хоть одну
запись, перестанет работать почта — а на неё приходят заявки. Поэтому зону
нужно выписать целиком, сверить запись за записью и только потом менять NS.

**Б. `www` на CDN, корень — редирект на `www`.** NS не трогаем, риск для почты
нулевой. Но главным адресом сайта становится `www.абхазберег.рф`, а это смена
главного зеркала: для поисковых систем заметное событие, и все ссылки, визитки
и реклама на адрес без www пойдут через переадресацию. Плюс сам редирект надо
где-то разместить — в России и с HTTPS, то есть завести ещё один сервис.

### Рекомендация
