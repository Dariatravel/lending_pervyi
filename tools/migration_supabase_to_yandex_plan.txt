# План миграции: Supabase → Яндекс (полный выход)

Проект: абхазберег.рф
Цель: убрать Supabase из продакшн-цепочки сайта. Медиа хранить в Яндекс Object Storage, каталог и служебные данные — в версионируемых JSON-снимках/локальных файлах, которые можно публиковать на GitHub Pages и при необходимости дублировать в Яндекс Object Storage.

---

## Важно: что именно переносим

| Что | Где сейчас | Куда на Яндексе |
|-----|------------|-----------------|
| **Файлы** (фото, видео) | Storage `site-media` | **Object Storage** `abhazbereg-media` |
| **Структура каталога** (объекты, медиа-метаданные, фильтры) | Postgres `listings`, `listing_media` | **JSON-снимки** в `data/` + копия в Яндекс Object Storage |
| **Рантайм-чтение в браузере** | `scripts.js` читает Supabase REST через `@supabase/supabase-js` | `scripts.js` читает локальный/Яндекс JSON |
| **Пайплайн генерации** | часть скриптов читает/пишет Supabase | Telegram + Google Sheets → JSON snapshot → HTML |

Postgres нельзя «перелить» в Object Storage как живую БД. Для статического сайта правильная замена — **детерминированный JSON-снимок каталога** плюс генераторы, которые читают этот снимок. Yandex Managed PostgreSQL нужен только если появится требование к настоящей SQL-БД.

## Правила безопасности миграции

1. **Не удалять Supabase-данные до двух успешных проверок прода.**
2. **Каждый этап заканчивать отдельным коммитом и push.**
3. **Перед удалением Storage делать dry-run Яндекса и `rg`-проверки.**
4. **Для БД сначала dual-run:** Supabase остаётся источником, параллельно генерируем JSON и сравниваем результат.
5. **Cutover делать только после parity-аудита:** HTML/карточки/фильтры/похожие объекты совпадают.
6. **Rollback должен быть простым:** пока Supabase не удалён, можно вернуть чтение из Supabase одним revert.

## Порядок и риски

```
0 (фото) → 1 (инвентаризация) → 2 (видео) → 3 (URL layer) → 4 (snapshot) → 5 (browser) → 6 (sync) → 7 (off)
```

| Риск | Снижение риска |
|------|----------------|
| Большие видео, egress Яндекс | Сжатые версии `-1800k.mp4` уже есть; мониторить трафик и Range-запросы |
| Сломать «похожие объекты» | Этап 5 только после parity snapshot |
| Два источника правды | На этапах 4–6: Supabase остаётся read-only fallback, snapshot сравнивается отчётом |
| Регрессия URL | После каждого этапа: `rg`-проверки + выборочный просмотр прода |
| Потерять объект/фильтр при отказе от Postgres | Перед cutover: архив, parity-аудит, count по source_kind, diff slug lists |
| Удалить Storage раньше времени | Удаление только после двух успешных прод-проверок и свежего dry-run |
